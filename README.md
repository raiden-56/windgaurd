# WINDGUARD

**Workforce Attendance & Site Operations Management Platform**
*Every Shift. Every Worker. Accounted For.*

WINDGUARD replaces the paper attendance register and muster roll for security guards, supervisors and site staff at wind farms, substations and remote facilities. Workers never sign in: **supervisors and administrators record attendance on their behalf**, and every entry and change is kept in an append-only audit trail.

It is an installable PWA that keeps working when the network drops at a remote site.

## Quick start (local)

Requirements: Node.js 20+ (tested on 24). No Docker, system PostgreSQL or Redis needed for local development.

```bash
npm install
npm run db:local          # terminal 1 — starts a self-contained PostgreSQL 18 on port 54331 (data in ./.devdb)
npm run db:migrate        # terminal 2 — applies migrations
npm run db:seed           # loads demo data (wipes existing data)
npm run dev               # db + API (port 4000) + web (port 3100)
```

`npm run dev` starts the database too, so after the first setup it is the only command you need.

Open **http://localhost:3100** and sign in with a demo account (password for all: `Windguard@2026`):

| `supervisor@windguard.local` | Site Supervisor – Nakhatrana (can manage roster) |

The demo organization, sites and ~76 workers are **sample data** generated by `apps/api/prisma/seed.ts` (120 days of attendance history relative to the moment you seed). Re-run `npm run db:seed` any time to get a fresh "today".

Production-style run: `npm run build` then `npm start` (the service worker / offline mode is only registered in production builds).

### Browser demo (GitHub Pages)

**Live demo: https://raiden-56.github.io/windgaurd/** — sign in with any demo account above.

GitHub Pages only serves static files, so the demo build runs the **real API inside the visitor's browser**: `apps/demo` bundles the NestJS controllers, services, attendance engine and seed into a Web Worker, backed by [PGlite](https://pglite.dev) (PostgreSQL compiled to WebAssembly) and stored in the browser's IndexedDB. The same migrations — including the audit-log trigger — create the schema. The web app is exported as static pages and sends its `/api` calls to that worker instead of the network.

What this means for visitors:

- The first visit downloads ~25 MB (the database engine and the API) and generates the sample data in about 15 seconds; later visits open in a moment.
- Data lives **only in that browser**. Nothing is shared between visitors or devices. The **Demo** chip in the top bar resets the data to a fresh "today".
- One tab at a time owns the database; a second tab offers to take over.
- Push notifications and offline mode (service worker) are not part of the demo; passkeys work only on browsers that support them for the `github.io` domain.

Build and publish:

```bash
npm run pages:build     # apps/web/out — static site under /windgaurd
npm run pages:deploy    # build + push to the gh-pages branch
```

The workflow in `.github/workflows/pages.yml` redeploys on every push to `main`. In the repository settings, **Pages → Build and deployment** must be set to *Deploy from a branch*, branch `gh-pages`, folder `/ (root)`. To preview locally: `node apps/demo/scripts/serve.mjs apps/web/out /windgaurd 3200` → http://localhost:3200/windgaurd/.

## Architecture

```
apps/
  demo/  Browser build of the API for GitHub Pages: esbuild bundle + PGlite (see "Browser demo")
  api/   NestJS 11 · Prisma 7 · PostgreSQL · BullMQ (optional Redis) · SimpleWebAuthn · ExcelJS · PDFKit
  web/   Next.js 16 (App Router) · React 19 · Tailwind CSS 4 · Radix primitives · TanStack Query/Table
         React Hook Form + Zod · Recharts · Motion · IndexedDB (idb) · Service worker
scripts/ dev-db.mjs (embedded Postgres), dev.mjs, start.mjs
```

- The web app proxies `/api/*` to the API (`next.config.ts` rewrites), so the session cookie is first-party (`httpOnly`, `SameSite=Lax`).
- **All attendance business logic lives in the API** (`apps/api/src/modules/attendance`). The pure calculation engine is `attendance.engine.ts`.
- **Multi-tenancy**: every organizational table carries `organizationId`; supervisors are additionally scoped to their assigned sites on every query.
- **Background jobs**: `QueueService` uses BullMQ when `REDIS_URL` is set and runs jobs in-process otherwise. Used for bulk employee imports and the 10-minute operational sweep (missing check-outs, unfilled shifts, attendance not completed, stale handovers).

### Key data rules

| Rule | Implementation |
|---|---|
| No duplicate attendance per employee/shift/work date | unique index `(employeeId, shiftId, workDate)` + upserts in transactions |
| Overnight shifts | `workDate` is the shift **start** date in the site's timezone; `shiftWindow()` adds a day when end ≤ start, so a 22:00–06:00 checkout stays on the original date |
| UTC storage | instants are `timestamptz`; calendar days are `DATE`; each site stores its own IANA timezone |
| Working hours | check-out − check-in, minus the shift break once the span reaches the half-day threshold |
| Late | check-in after scheduled start + the shift's grace period |
| Overtime | net worked minutes beyond scheduled net duration, once past the organization threshold |
| Half day | checked-out shifts shorter than the half-day threshold |
| Approved leave ≠ absence | approved leave records auto-materialize as `LEAVE`; excluded from the attendance-% denominator (configurable) |
| No silent overwrites | once a register is submitted, changes go through **corrections** (previous vs proposed values, admin approval) |
| Duplicate check-ins | rejected with 409 — use a correction |
| Manual times | require a reason, stored on the record and in the audit log |
| Audit immutability | a PostgreSQL trigger rejects `UPDATE`/`DELETE` on `AuditLog` |
| Soft delete | archiving an employee hides the master record; attendance history is never deleted |

### Offline attendance

1. When a supervisor opens a register online, a **minimal roster** (ID, name, designation, location, current status/version — no phone numbers or addresses) is saved to IndexedDB and pruned after 3 days. Supervisors' other shifts for the day are prefetched.
2. Offline, the register loads from IndexedDB and every action is queued with a **client-generated ID**, the **device timestamp** and the record version the device last saw.
3. On reconnect (or via Background Sync in the service worker) the queue is posted to `POST /api/attendance/sync`.
4. The server applies actions idempotently per client ID, records the **actual sync time separately**, marks records `entryMode = OFFLINE`, and reports a **CONFLICT** — never overwriting — when the server record changed since the device's snapshot. Conflicts can be resolved from *Attendance → Offline sync* by keeping the server value or raising a correction.

### Passkeys (WebAuthn / FIDO2)

- Registration and authentication ceremonies via `@simplewebauthn/server` + `@simplewebauthn/browser`; discoverable credentials, user verification required.
- Only the credential ID, public key, counter and transports are stored. Biometrics never leave the device.
- Fallback: email + password. Recovery: an administrator issues a one-time, 24-hour recovery code (Supervisor Management → ⋯ → Issue recovery code).
- **Testing on phones** requires HTTPS on a real domain (or a tunnel). Set `RP_ID` to the domain and `WEB_ORIGIN` to the full origin in `apps/api/.env`. `localhost` works for desktop testing.

### Push notifications (optional)

Generate keys with `npx web-push generate-vapid-keys` and set `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` in `apps/api/.env`. Users enable push per device from the Notifications page. In-app notifications work without this.

## Configuration (`apps/api/.env`)

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | PostgreSQL connection string |
| `JWT_SECRET` | Session signing secret — **must be changed for production** (the API refuses to start in production with the dev value) |
| `RP_ID`, `RP_NAME`, `WEB_ORIGIN` | WebAuthn relying party and allowed web origin(s) |
| `REDIS_URL` | Optional; enables BullMQ |
| `VAPID_*` | Optional; enables Web Push |
| `PORT` | API port (default 4000) |

Web: `API_URL` (default `http://localhost:4000`) for the `/api` proxy.

## Feature map

- **Overview** — live KPIs, today's shift board, attention list, trends (daily/weekly/monthly/yearly), site workforce, shift distribution, activity feed; a mobile-first view for supervisors.
- **Attendance** — daily register by site/date/shift; Present/Absent/Leave/Half-day, Check in/out, manual times with reasons, bulk and "mark all present", remarks, submit → approve/lock/reopen; all-records view; approvals queue; corrections; offline sync.
- **Shift management** — configurable shifts (break, grace, required workers, supervisor, active days) with a 24-hour timeline; weekly roster calendar with understaffed/overlap detection, copy previous day, duplicate week, generate from defaults; shift handovers with confirmation.
- **Employees** — searchable/sortable/paginated directory with column customization, filters, bulk actions, export; profiles with attendance heatmap, site history, leave records.
- **Supervisors** — application users, roles, site assignments, extra grants, recovery codes, session revocation.
- **Sites** — projects → sites → deployment points; site dashboards; cross-site comparison.
- **Reports** — daily, weekly, monthly, quarterly, yearly, custom; filters by project/site/employee/designation/supervisor/shift/status; XLSX, PDF, CSV with official header and signature lines.
- **Digital muster roll** — monthly date matrix with configurable abbreviations, totals, certification by the register keeper; print, PDF, Excel.
- **Workforce analytics**, **Import / Export** (10-step validated Excel/CSV import with error reports), **Gate register**, **Audit logs**, **Notifications**, **Settings** (profile, passkeys, attendance rules, holidays, organizations, help).
